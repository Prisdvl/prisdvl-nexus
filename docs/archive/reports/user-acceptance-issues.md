# User Acceptance Issues

真实用户验收（Real User Acceptance）问题清单。与自动化测试的 `mvn test` / E2E 不同，
这里记录的是**以新用户身份实际操作时**暴露出来的问题——根因、最小修复与验证方式。

- 验收环境：`http://localhost:8088`（nginx + Vue 静态产物 + Spring Boot + 8 容器全 healthy）
- 验收方法：先读真实代码确认根因（不依据 README 猜测），再改，再真机复验
- 状态取值：`Fixed` / `Won't Fix` / `Open`

## P0

### UA-001　知识库列表页：取消文件选择后按钮永久 loading

- **严重程度**：P0（状态永远卡住，且用户唯一的出路是刷新页面）
- **现象**：在知识库列表页点「上传 Vault」→ 系统文件选择器弹出 → 点「取消」→ 按钮一直转圈，页面无法恢复。
- **复现步骤**：
  1. 登录 → 知识库列表页
  2. 任一知识库卡片点「上传 Vault」
  3. 系统弹窗中点击「取消」
- **实际结果**：该卡片的按钮进入 loading 并**永不退出**，只能 F5 整页刷新。
- **期望结果**：取消 = 什么都不发生，界面与点击前完全一致。
- **根因**：`web/src/views/KnowledgeBaseListView.vue` 的 `pickFile()` 在 `input.click()`
  **之前**就执行了 `uploading.value = kb.id`，而复位语句写在 `input.onchange` 里。
  用户在系统弹窗里点「取消」时，浏览器**不会派发 `change` 事件**（连 `files` 为空也不派发），
  于是复位那行永远不执行 —— 这不是"少了个兜底"，是状态机的**顺序**错了。
  （同一产品的 `KnowledgeBaseDetailView.vue:pickUpload()` 没有这个 bug，正因为它没有提前置位。）
- **修复方案**：抽出统一的 `pickImport()`：不在打开选择器前碰 loading；拿到文件才置位；
  用 `finally` 无条件复位；取消（`files` 为空）直接 `return`。两处实现对齐同一种写法。
- **验证方式**：`npm run build`（含 `vue-tsc --noEmit`）通过；真机 E2E 脚本 `verify-real-user-flow.mjs`
  对"取消后按钮回到可点状态"做断言。
- **状态**：Fixed

## P1

### UA-002　「欢迎回来，undefined」——并污染了 localStorage

- **严重程度**：P1（核心链路：注册/登录后的第一句反馈；且污染会跨会话残留）
- **现象**：登录成功后提示"欢迎回来，undefined"；侧栏账号名在 profile 请求返回前也显示 `undefined`。
- **复现步骤**：任意账号登录 → 观察右上角/侧栏提示。
- **实际结果**：`欢迎回来，undefined`。
- **期望结果**：`欢迎回来，<用户名>`。
- **根因**（完整链路，非表面文案问题）：
  1. 服务端 `AuthTokenResponse` 的形状是
     `{ accessToken, tokenType, expiresIn, user: UserInfoResponse }` —— **没有顶层 `username`**，
     用户名在 `user` 里（`nexus-app/.../auth/model/dto/AuthTokenResponse.java`）。
  2. 前端 `web/src/api/knowledge.ts` 却声明成扁平的 `username: string`。
  3. TypeScript 的 `interface` **只活在编译期、运行时不校验**，所以
     `result.username` 取到 `undefined` —— 类型系统不会报错，编译器帮不了这个忙。
  4. 次生污染：`saveSession(result.accessToken, result.username)` 把**字符串 `"undefined"`**
     写进了 `localStorage['nexus.username']`，比留空更难排查。
- **修复方案**：
  - `LoginResponse` 形状与服务端 DTO 对齐（内嵌 `user: UserInfo`）；
  - `LoginView` 取 `result.user?.username`，并兜底为表单里刚输入的用户名；
  - `saveSession()` 过滤假值，任何情况下都不把 `"undefined"` 落盘。
- **验证方式**：`vue-tsc` 通过；真机登录断言提示文案匹配 `^欢迎回来，\S+$` 且不含 `undefined`，
  并断言 `localStorage.nexus.username !== 'undefined'`。
- **状态**：Fixed

### UA-003　新用户 Chat 首页出现开发者 Demo 问题

- **严重程度**：P1（新用户第一次进入核心页面看到的就是"别人的资料"）
- **现象**：**0 知识库**的新用户进入「对话」页，看到固定三问：
  「我的笔记里缓存击穿怎么解决？」「线程池的核心参数有哪些坑？」「G1 和 ZGC 该怎么选？」
- **复现步骤**：注册新账号 → 进入「对话」页 → 观察欢迎区。
- **实际结果**：显示上述三个硬编码技术问题。
- **期望结果**：无知识库的新用户应看到空态与引导（"还没有知识库 → 导入资料"）。
- **根因**：`web/src/views/AgentView.vue` 中 `const samples = [...]` **硬编码**在脚本里，
  模板的欢迎区以 `v-if="!items.length"` 渲染 —— 只判断"有没有消息"，**不判断有没有知识库**，
  所以新用户必然看到它们。
- **修复方案**：
  - `samples` 改为 `computed`：知识库为空时返回 `[]`；
  - 欢迎区按状态分支渲染：无库 → 「还没有知识库」+ 「导入资料」按钮；
    有库 → 用**用户自己的库名**生成示例（`《<库名>》里主要讲了什么？`），该问题确实能命中他的资料。
  - 同类清理：
    - `AgentsView.applyTestQuestion()`：改用用户自己的库名构造试跑问题；
    - `KnowledgeBaseDetailView` 两处 placeholder 由"缓存击穿…"改为中性引导。
- **验证方式**：真机 E2E 断言新用户欢迎区**不出现**上述任一字符串，且出现"还没有知识库"。
- **状态**：Fixed

### UA-014　导入显示「已完成」，但检索 0 命中（可检索性有一个隐形前置步骤）

- **严重程度**：P1（核心链路断裂：导入资料 → 基于资料问答，中间隔着一个用户不知道的步骤）
- **现象**：上传文件后任务状态变成 `DONE`、切片数正常、失败 0；接着去问答 / 检索，
  **一条都命中不了**。
- **复现步骤**：
  1. 新建知识库 → 导入任意 `TXT / MD / PDF / DOCX`
  2. 等界面显示导入「已完成」
  3. 用文件里的独有标记去检索
- **实际结果**：检索 0 命中。（实测：五种格式全部 `DONE`、切片数正常，检索全为 0。）
- **期望结果**：导入完成即可检索，或界面在导入阶段就明确推进"建立索引中"。
- **根因**：`ImportTaskExecutor` **只做"解析 + 分块"，没有任何 embedding / index 调用**；
  可检索性由**另一个接口** `GET /workflow/run/{kbId}`（统计文档 → 统计切片 → 向量化 → 建索引）负责。
  也就是说，"向量化"与"建索引"是两个**概念上不该让最终用户理解**的隐性前提，
  而导入任务的状态却直接显示为"已完成"。
  产品自己也知道这个坑——详情页检索失败时会提示「确认已『向量化』与『建索引』」，
  但那已经是**失败之后**的补救，用户在此之前无从知晓。
- **修复方案**：导入进入终态（`DONE` / `PARTIAL`）后**自动串接** `workflow/run`，
  状态文案统一为"解析中 → 建立索引中 → 已完成"，用户不必知道向量化是什么。
  workflow 四步是增量的（只处理待向量化 / 待建索引的切片），重复执行安全；
  失败时降级为提示"可到详情页手动执行"，不阻断已完成的导入。
- **验证方式**：`web/scripts/verify-import-formats.mjs` —— 五种格式各自上传含独有事实的文件，
  **先断言"导入 DONE"再断言"独有事实可检索"**；不跑索引步骤时该脚本会失败，
  证明这条断言真的在测可检索性而不是测接口返回值。
- **状态**：Fixed

### UA-015　Vault（ZIP）导入是全量同步，界面上没有任何事前警示

- **严重程度**：P1（属于"危险操作未确认"——会静默删除用户已有的文档）
- **现象**：知识库详情页点「上传 Vault」会直接把 ZIP 传上去。
  而 Vault 导入是**全量同步语义：清单里没有的文档会被删除**（连同切片与向量索引）。
- **复现步骤**：
  1. 一个已有若干文档的知识库
  2. 上传一个只含一两篇文档的 ZIP（Vault）
  3. 观察结果
- **实际结果**：库里原有的、不在 ZIP 清单中的文档**被静默删除**。
  界面上没有任何事前提示，用户只能在导入结果里看到一行"删除 N"。
- **期望结果**：上传前明确告知"这是整包同步，清单外的文档会被删除"，并由用户确认。
- **根因**：`KnowledgeBaseDetailView` 的 `pickFile()` 直接调用 `uploadVault`，
  没有确认步骤。语义本身是对的（Vault 同步就该是全量），**缺的是告知**。
  （本次是写多格式验收脚本时踩到的：把 ZIP 与四个单文件放进同一个库，
  最后传的 ZIP 把前四个全删了，于是"导入全 DONE、索引全 SUCCESS，检索却只剩 1 条"。）
- **修复方案**：`pickFile()` 前加一道确认闸门，说明"ZIP 里没有的文档会被删除"，
  并引导"只想追加资料请用『上传文件』"。取消则不打开文件选择器。
- **验证方式**：真机点击后出现确认框；取消时不发起任何请求。
- **状态**：Fixed

### UA-016　Agent 对话页「流式输出」是假的：整段回答一次性出现

- **严重程度**：P1（产品的招牌能力失效——用户等了十几秒，期间界面**一个字都不显示**）
- **现象**：在「对话」页（Agent 模式）提问，助手气泡长时间空白，
  然后**整段答案一次性跳出**；期间工具痕迹（`检索中 → 检索完成`）也完全不出现。
- **复现步骤**：
  1. 打开「对话」页，新开会话（默认 Agent 模式）
  2. 提一个需要长回答的问题
  3. 盯着助手气泡看
- **实际结果**：气泡在生成期间保持空白（实测 **0 字节 → 16 秒无任何文字**），
  生成结束时整段答案连同工具痕迹一起出现。
- **期望结果**：文字应逐字增长（这是流式问答的全部价值）；工具痕迹应在生成前就出现。
- **根因（已实测定位，不是推断）**：
  - **传输层是正常的**。用 `fetch` tee 探针测量字节到达时刻，证明浏览器**持续收到帧**：
    264 个块 / 31 KB，从 14.5s 起每 ~40ms 一块——正是模型逐字输出。
  - **问题在前端响应式**：`AgentView.send()` 里
    `const answer: ChatItem = {...}` 是**普通对象**，`items.value.push(answer)` 之后
    仍以 `answer.content += text` 原地改写它。`ref` 数组的 `push` 只追踪数组结构，
    推入的**原始对象**后续改写不经过 Proxy 的 `set` 陷阱，**不触发重渲染**。
    于是视图一动不动，直到 `finally` 里 `items.value = toItems(...)` 整体替换数组才有一次刷新
    ——这正是"憋到最后一次性出现"。
  - 对照：知识库详情页的 RAG 问答用 `streamedText.value += text`（**走 `.value` 代理**），
    所以同一条链路在那边是正常的。这也解释了为什么既有脚本没抓到它：
    `verify-stream.mjs` 测的是 RAG 页，`verify-agent-chat.mjs` 只断言**最终** Markdown 出现，
    两者都没有对**对话页**断言"文本在增长"。
- **修复方案（最小改动）**：把 `answer` 由普通字面量改为 `reactive<ChatItem>({...})`
  （`AgentView.vue` 引入 `reactive`）。此后 `answer.content/toolCalls/retrieval/citations/streaming`
  的全部写入都经过代理，逐帧驱动视图。一行 import + 一处声明，不动任何链路逻辑。
- **验证方式**：
  - 字节探针复测：`streamLen` 由"全程 0"变为持续增长（175 → 881 → 1785 → … → 6288）。
  - 新增 `web/scripts/verify-stop.mjs`（§30 停止生成）在修复前因"等不到正文增长"**必然超时失败**，
    修复后 **15 / 15 通过** —— 它同时是这条缺陷的回归网。
  - 全仓横向排查同类反模式（`ref 数组.push(原始对象)` 后再改写）：**仅此一例**，
    另两处 push 推入的都是不再改写的静态快照。
- **状态**：Fixed

### UA-018　删除会话不清理它的会话记忆（`SPRING_AI_CHAT_MEMORY` 留下无主数据）

- **严重程度**：P1（产品级级联缺口；真实用户删除会话同样中招）
- **现象**：`ConversationServiceImpl.delete()` 只做两件事——软删会话（`@TableLogic` 改写为
  `UPDATE deleted=1`）、物理删 `chat_message`。而 `SPRING_AI_CHAT_MEMORY`
  （key = `conv:{conversationId}`，见 `ChatMemoryKeys`）**从来没有被清理过**。
  实测该表 **415 行**：demo 392 / Prisdvl 3 / 10 个测试账号各 2 ——
  也就是凡是被删掉的会话，它的记忆行都留在了表里。
- **为什么这不只是"多几行垃圾"**：这张表是"这次请求发给模型多少历史"的**唯一来源**。
  会话 id 是雪花号，正常情况下不会复用，所以复现窗口很窄；但一旦该 key 被重新读到
  （重建会话 / id 复用 / 数据修复），新会话就会**凭空记得旧会话说过的话**。
  这类问题不会自己暴露，只能靠断言把形状钉住。
- **修复方案**：在删消息之后追加一行，且走 Spring AI 的抽象层而不是裸 SQL ——
  key 的构造规则只在 `ChatMemoryKeys` 一处，在这里重新拼一遍字符串等于把它复制成两份：

  ```java
  chatMemory.clear(ChatMemoryKeys.of(conversationId));
  ```

  同时把类注释里的"删除 = 软删会话 + 物理删消息"更新为"…+ 清空会话记忆"。
  构造函数相应新增 `ChatMemory` 依赖（无循环：`ChatMemory` 只依赖仓库与配置值）。
- **验证方式**：新增 `ConversationDeleteClearsMemoryTest`（4 项，`@ActiveProfiles("test")`）。
  **它不调用模型、也不需要 `AI_CHAT_API_KEY`，因此永远会跑**——一条"只在本地配了 Key
  才执行"的断言等于没有断言：
  ① 删除后记忆为空；② 删 A 不动 B（A/B 会话独立性）；③ 没有记忆的会话也能删
  （`clear` 空 key 是 no-op —— 这是最常见的情形，PLAIN 会话根本不写记忆）；
  ④ 越权删除抛异常且**记忆未被清**（归属校验必须发生在删除之前，
  否则一次越权请求虽报错、却已产生真实破坏）。实测 **4 / 4 通过**。
- **状态**：Fixed

### UA-017　用户停止生成后，后端把一次"正常中止"记成 ERROR 级未预期异常

- **严重程度**：P3（不影响用户；影响的是运维——日志与指标失真）
- **现象**：用户点「停止」后，后端日志出现一条 ERROR：
  `AsyncRequestNotUsableException: Response not usable after response errors`
  （抛出点 `ChatStreamServiceImpl.stopAndFinalize:551`），并经
  `GlobalExceptionHandler` 记为 **"未预期异常"**；同时
  `observabilityRegistry.increment(ERRORS)` 让"对话失败次数"指标 +1。
- **复现步骤**：在对话页发起一轮生成，请求已开流后立即点「停止」。
- **实际结果**：客户端已断开是**预期内**的（用户刚刚中止），
  但终端路径里仍会 `send(SSE done 帧)` → 写已关闭的响应 → 抛异常 →
  被当成"未预期异常"。
- **期望结果**：客户端断开属于**正常终止**，应静默跳过推送（最多 DEBUG/WARN），
  且不计入错误指标。
- **根因**：`stopAndFinalize()` / `onComplete()` / `onError()` 都无条件调用 `send(...)`；
  只有 `abandon()`（客户端断开路径）不推送，因此不触发。用户点停止时，
  前端 `stop()` 会**先调 stop 接口、再 abort 本地连接**，
  服务端 `stopAndFinalize` 与客户端断开几乎同时发生，于是落进这条路径。
- **最小修复建议**（本次未实施，避免为 P3 重建后端）：`send()` 内部捕获
  `IOException / AsyncRequestNotUsableException` 并降级为 WARN 日志；
  或在这三条终态路径推送前判断 `response.isCommitted()` / 连接存活。
- **状态**：Open（已记录，进 `docs/future-improvements.md`）

**两个必须写下来的运行陷阱：**

1. **`.demo-token` 只有 30 分钟寿命**（`nexus.jwt.access-token-ttl: 30m`）。
   长脚本（如 `verify-stream.mjs` 带 180s 超时）很容易**跑着跑着令牌就过期**，
   表现为莫名其妙的超时。跑之前先刷新：
   ```bash
   curl -s -X POST -H 'Content-Type: application/json' \
     -d '{"username":"demo","password":"Demo@12345"}' \
     http://localhost:8088/api/auth/login \
     | python -c "import sys,json;print(json.load(sys.stdin)['data']['accessToken'],end='')" > web/.demo-token
   ```
2. **地址口径不统一**：这批脚本的 `API_BASE` 默认是 `http://localhost:8080`（后端容器**内部**端口）。
   Docker 部署下宿主机**没有暴露 8080**，只有 nginx 的 8088，直接跑会以 `fetch failed` 失败 ——
   看起来像"脚本坏了"，实际是地址没给对。且两者对 `/api` 的处理**不一致**：
   `verify-security` 自己拼 `/api/...`（`API_BASE` 不带 `/api`），
   `verify-agent-no-kb` 的默认值里**含** `/api`（`API_BASE` 要带）。按各脚本的默认值反推最稳。

这 9 个脚本**都自带收尾**（会话 / Agent / 知识库跑完即删，实测 HTTP 200），
再次印证 `verify-stop.mjs` 缺收尾是唯一的例外（已补）。

### 本轮（§30 停止生成 + 流式复核）的关键收获

1. **"看着能用"与"真的能用"差一个时间维度。** UA-016 之前一直没被发现：
   接口 200、内容最终正确、既有脚本全绿 —— 但对话页在生成的十几秒里**一个字都不显示**。
   只有断言"文本在增长"才能证伪，而所有既有脚本断的都是**终态**。
2. **定位顺序：先证传输，再判渲染。** 用 `fetch` tee 探针量出"字节每 40ms 到一批"，
   才把嫌疑从网络/nginx 收敛到前端响应式；若反过来先去改 nginx，就会白改一轮。
3. **停止功能自己也暴露了一个后端小毛刺**（UA-017）：客户端断开后仍推送终帧，
   被记成 ERROR。对用户无影响，已归档。
4. **验收脚本本身也会变成污染源。** 新写的 `verify-stop.mjs` 第一版没有收尾，
   每跑一次就在 demo 名下留两个会话 —— 跑了三轮就是 6 个。
   写验收脚本时，"跑完不留垃圾"应当和断言一样是硬要求（现已补上）。
5. **"残留 0"这种结论必须连口径一起写。** 上一版只扫三个用户名前缀就下结论，
   漏掉了用别的前缀建库的脚本。结论的可靠性取决于**核查范围是否覆盖全集**，
   而"我扫过的前缀"不等于"全部账号"。
6. **没被复跑的测试等于不存在。** `verify-stream.mjs` 早就因 UA-003 的文案改动而失效，
   却一直显示"存在"。把仓库里**全部**脚本都跑一遍（而不是只跑记录里那几个）才暴露出来。
   同理，本轮还补上了此前**无人断言**的一条要求：「引用刷新后仍在」——
   既有脚本只断过"工具痕迹刷新后仍在"，字段相邻，很容易误以为覆盖了。
