# 十、Phase 3：Retriever 端口抽象

这是首先要做的事情。

当前已经有：

```text
pgvector
ES
IK
Hybrid Search
RRF
Rerank
```

现在不要继续把具体实现直接暴露给业务层。

建立统一 Retriever 抽象。

例如：

```java
public interface Retriever {
    List<RetrievedDocument> retrieve(RetrievalQuery query);
}
```

根据现有项目实际情况设计接口，不要求照抄上面的代码。

需要能够支持：

```text
VectorRetriever
KeywordRetriever
HybridRetriever
RerankRetriever
```

最终形成：

```text
RagService
   ↓
Retriever
   ↓
具体 Retrieval Strategy
```

而不是：

```text
RagService
   ↓
ElasticsearchClient
   +
PgVector
   +
RRF
   +
Rerank
```

全部硬编码在一个 Service 中。

# 二十一、`approval_required`

必须真正实现，而不只是文档声明。

执行流程：

```text
Agent
 ↓
准备调用 Tool
 ↓
检查 Tool Policy
 ↓
approval_required = true
 ↓
暂停 Agent
 ↓
产生 Approval Request
 ↓
SSE 推送给前端
 ↓
用户批准 / 拒绝
 ↓
继续 / 终止
```

例如：

```json
{
  "type": "approval_required",
  "tool": "http_request",
  "description": "即将访问指定外部 API",
  "approvalId": "..."
}
```

用户：

```text
批准
```

Agent：

```text
继续 Tool Call
```

或者：

```text
拒绝
```

Agent：

```text
终止当前 Tool 调用
```

# 六十一、安全验收

必须专门测试以下情况：

### 用户隔离

```text
User A
不能访问
User B
```

### Workspace 隔离

```text
Workspace A
不能读取
Workspace B
```

### KnowledgeBase 隔离

Agent A 不能检索未授权 Knowledge Base。

### Tool 权限

普通用户不能调用管理员 Tool。

### API Key

任何 API 都不能返回完整 key。

### Prompt Injection

RAG 内容中的恶意指令不能直接改变系统级指令。

### Approval

需要人工确认的 Tool 必须暂停，而不是自动执行。

### Audit

关键 Tool / Workflow / Approval 行为必须留痕。
